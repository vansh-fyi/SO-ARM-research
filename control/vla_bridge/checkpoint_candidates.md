## pi0 / pi05 selection (Plan 14-04, hand-written; the script never rewrites this section)

**Chosen:** `pi0` -> `amindt/pi0_so101_pickandplace_redblue` @ `6d052c61e84eec978070c361d7f86e7d71e08b4f`;
`pi05` -> `yathAg/pi05_so101_pick_place` @ `8913fc8168dfada97c676598897ac3deaaaf6f0d`
(`backend_configs/pi0.json`, `backend_configs/pi05.json`).

Why these two (checked live 2026-10-01):
- **Genuine SO-101 joint-space fine-tunes**, so no base/OXE checkpoint and no IK layer. Each one's
  training dataset `meta/info.json` (`amindt/so101_pickandplace_redblue`, `yathAg/so101_pick_place`;
  lerobot dataset v3.0, 30 fps) names `observation.state` and `action` as exactly
  `shoulder_pan.pos ... gripper.pos`, the same 6 keys and order as `action_contract.JOINT_ORDER`.
  Both checkpoints were fine-tuned from the official base (`pretrained_path`: `lerobot/pi0_base` /
  `lerobot/pi05_base`).
- **The only candidates that pass the gRPC-bridge key check.** Installed lerobot 0.6.1 delivers
  only `observation.images.camera1` (our wrist frame) plus `observation.state` and `task` to the
  PolicyServer (see `BRIDGE_IMAGE_KEY` in `check_checkpoint.py`). A checkpoint must declare
  `camera1`, or `prepare_raw_observation()` raises KeyError on every observation. The other
  declared camera (`camera2`) arrives missing and pi0/pi05 mask it as an empty camera
  (`_preprocess_images`, `missing_img_keys`). A wide search (about 1250 pi0/pi05 repos from 19 HF
  queries) found 13 with a `camera1` key. These two are the clearest SO-101 matches with a plain
  6-D state/action. The others: `yathAg/pi05_so101_pick_place_fp16` (an fp16 copy of the pick);
  `zrgong/*` (also declare `observation.state.ee`, which the bridge never sends);
  `Harrysunshine/so101-pi0-lora-sim-real-10task` (`camera0/1/2`, sim+real mix);
  `tonghuiwang123/so100-pi0*` (SO-100); `grahamwichhh/pi05_*` (4 cameras, robot not stated);
  `lerobot/pi0_old` (pre-processor-pipeline config format).
- **Loadable by the installed lerobot 0.6.1.** Each `config.json` parses with
  `PreTrainedConfig.from_pretrained` (to `PI0Config` / `PI05Config`). Every step in their
  `policy_preprocessor.json` / `policy_postprocessor.json` is registered in 0.6.1's
  `ProcessorStepRegistry`. Both are public, not gated, Apache-2.0, `library_name: lerobot`.
- **Base checkpoints are not usable on this bridge.** `lerobot/pi0_base` / `lerobot/pi05_base`
  declare `base_0_rgb / left_wrist_0_rgb / right_wrist_0_rgb` (KeyError) and a 32-D padded
  action space with no SO-101 normalization stats.

Not verified (stated so the next reader doesn't assume it):
- Which physical camera `camera1` was in each training dataset. On our rig `camera1` is the wrist
  camera, so if the dataset's `camera1` was an overhead view the policy sees a mismatched
  viewpoint. That affects task success, not whether actions flow.
- Unit convention of the training data's `.pos` values (degrees vs the `-100..100` range), the
  same open question as SmolVLA's checkpoint. Actions still pass through the unchanged
  `safety_validator.validate_action()`.
- Real inference: no GPU here, and the multi-GB weights were not downloaded.

Colab prerequisites (no new code cells): `lerobot[async]==0.6.1` already installed by the notebook
(the `pi` extra adds only `transformers>=5.4,<5.6` and `scipy`, the same transformers range SmolVLA
needs). The pi0/pi05 tokenizer step loads `google/paligemma-3b-pt-224`, which is **gated (manual
approval)** on the HF Hub, so the HF account behind the notebook's token must have accepted that
license. Both checkpoints are bf16 (about 3.5B params, about 7 GB), so prefer an L4/A100 runtime
over a T4.

## ACT selection (Plan 14-05, hand-written; the script never rewrites this section)

**Chosen:** `act` -> `hrl7/so101-pregrasp-act-l4` @ `1fb2021f5378c71f11ec95c76ecbdc066f61b5c2`
(`backend_configs/act.json`).

Why ACT needs a stricter key check than pi0/pi05 (installed lerobot 0.6.1, read 2026-10-01):
`ACTPolicy.predict_action_chunk()` builds `[batch[key] for key in self.config.image_features]`
and has no missing-camera masking. The bridge delivers only `observation.images.camera1`. So an
ACT checkpoint must declare `camera1` as its **only** image key:
- **No `camera1`:** `prepare_raw_observation()` raises KeyError.
- **`camera1` plus `camera2`/`camera3`:** `predict_action_chunk()` raises KeyError.

The server logs the error per observation, no action chunk comes back, and
`BridgeActionSource` holds position. `check_checkpoint.py` encodes this as
`NO_CAMERA_MASKING_BACKENDS` (the `gRPC-bridge key fit` column above).

Search (live, 2026-10-01, unauthenticated HF API):
- **Scope:**
  - 15 name searches (`act_so101`, `so101_act`, `act so100`, `lerobot act`, ...), giving 1809 repos
    whose name contains "act". Their `config.json` was fetched; about 1475 parsed as lerobot
    `type: act`.
  - Every `lerobot`+`act`-tagged repo (10851 in total) whose name mentions SO-100/SO-101 and wasn't
    already checked: 1702 more `config.json` fetches.
- **Result:** exactly two ACT checkpoints declare `camera1` as their only image key:
  `hrl7/so101-pregrasp-act-l4` and `pshingavi/policy_first-so101_22`. Everything else is
  multi-camera (`camera1`+`camera2`, e.g. the Alkatt/lerobotForScienceEdu/JustBubbles families) or
  single-camera under another name (`front`, `wrist`, `laptop`, ...). Both kinds fail on this
  bridge.
- **Official LeRobot ACT checkpoints** (`lerobot/act_aloha_sim_*`) are bimanual ALOHA sim policies:
  14-D, `observation.images.top`, no processor files. They can't be used here.

Why `hrl7/so101-pregrasp-act-l4` over `pshingavi/policy_first-so101_22`:
- **Units.** The normalizer stats (`policy_preprocessor_step_3_normalizer_processor.safetensors`)
  show `hrl7`'s state/action reaching 118 on wrist_roll, with the gripper at 1.9-47. That only fits
  degree-mode joints (`use_degrees=True`), which matches `action_contract.ACTION_UNITS` (degrees,
  absolute). `pshingavi`'s arm joints clamp at exactly -100.0/100.0, the signature of lerobot's
  `-100..100` range-normalized mode. That would be a unit mismatch against our degree-mode robot.
- **Data.** `hrl7`: 58 episodes, 17400 frames, 5000 steps at batch 32, chunk_size 100.
  `pshingavi`: 5 episodes, 3000 steps at batch 8.
- **Camera.** `hrl7`'s dataset is named `so101-wrist-d1-pregrasp-v1`, which suggests `camera1` was
  a wrist camera, the same viewpoint our `camera1` delivers. This is inferred from the name, not
  verified.
- **Both pass the load checks.**
  - Public, not gated, Apache-2.0, `library_name: lerobot`.
  - `PreTrainedConfig.from_pretrained` gives `ACTConfig` (image_features `[camera1]`, 6-D
    `observation.state`, no `env_state_feature`, `temporal_ensemble_coeff: null`).
  - Every pre/postprocessor step is registered in 0.6.1's `ProcessorStepRegistry`.
  - chunk_size 100 >= the bridge's `actions_per_chunk=50`.

Not verified (stated so the next reader doesn't assume it):
- **Joint names and order of `hrl7`'s training data.** Its dataset `hrl7/so101-wrist-d1-pregrasp-v1`
  is private (401), so `meta/info.json` couldn't be read. It is a 6-D SO-101 follower policy and
  standard SO-101 recordings use `JOINT_ORDER`, but that is an inference. For comparison,
  `pshingavi`'s public dataset does name exactly `shoulder_pan.pos ... gripper.pos`.
- **Task behaviour.** "pregrasp" suggests the policy moves toward a pre-grasp pose. With only
  5000 steps, a poor task outcome is expected and not a pipeline failure for D-05.
- **Real inference.** There is no GPU here.

Colab prerequisites (no new code cells): `lerobot[async]==0.6.1` already includes ACT (no extra).
The policy is a small ResNet-18 + transformer (`model.safetensors` about 200 MB), so a T4 runtime
is enough.

## RDT-1B selection (Plan 14-11, hand-written; the script never rewrites this section)

**Chosen default:** `robotics-diffusion-transformer/rdt-1b` @ `eb09036cc64ca4945051acbd1bd581d30a1d7711`,
action space `joint_position` (`backend_configs/rdt1b.json`). The official
`robotics-diffusion-transformer/rdt-170m` @ `8aa386c` is a reviewed alternate.

**Action space, confirmed rather than assumed.** It was checked against
`thu-ml/RoboticsDiffusionTransformer` @ `cd79363` and the weights:
- **Slot map.** `configs/state_vec.py` maps `right_arm_joint_{0..9}_pos` to slots 0-9 and
  `right_gripper_open` to slot 10.
- **README.** A single-arm robot fills the right-arm part; with 6 DOF, fill the first six joint
  slots. Physical quantities stay in SI units (radians), and only the gripper is min-max normalized
  to [0, 1].
- **State and action share the same slots.** `scripts/agilex_model.py` and
  `data/hdf5_vla_dataset.py` write the ABSOLUTE target qpos into the same slots as the state, and
  `train/train.py` passes the state indicator as the action mask.
- **Weights.** The final layer outputs 128 values, and the state adaptor takes 128 state + 128 mask
  values.

So SO-101's 5 arm joints map directly to slots 0-4, and its gripper (percent / 100) to slot 10. No IK
is needed. The client only converts units: radians to degrees, and [0, 1] to percent. The EEF slots
(30-38: an absolute position plus a 6-D rotation) are supported client-side as an `eef_pose` fallback
through `eef_to_joint.solve_ik()`, but no reviewed checkpoint uses them.

Caveats:
- **Out of distribution.** No SO-101 fine-tune exists, and the base checkpoint never saw SO-101's
  joint conventions. Expect the pipeline to run end to end, but not task-meaningful motion, until RDT
  is fine-tuned on SO-101 data (the upstream README's fine-tuning guide, ~150K steps recommended).
- **Compute.** The policy and encoders run in bf16, which a T4 lacks. T5-XXL (a 44.5 GB fp32
  download, ~9.5 GB in VRAM) dominates the footprint. Use an A100 runtime.
- **Pacing.** Each of the 64 chunk steps is an absolute target at 30 Hz. The server returns the step
  about one client control period ahead (step 14 at the default 2 Hz loop).
