## 1. lerobot#2210 status

[huggingface/lerobot#2210](https://github.com/huggingface/lerobot/issues/2210) reports a zero-shot
SmolVLA/SO-101 inference crash (`AssertionError: mean is infinity`). **This did not reproduce.**

The checkpoint used (`victorvanhalst/smolvla_so101_cube`, a fine-tuned SO-101 cube-manipulation
checkpoint selected in Plan 11-03) ran to `max_steps_reached` across a full 60-step episode without
raising that assertion or any other upstream inference exception. The three crashes hit during this
session's live testing were all traced to bugs in this project's own bridge code, not to #2210 or any
other upstream SmolVLA/lerobot issue:

1. `connect_bridge()` never started `receive_actions()`'s background thread, so the action queue was
   permanently empty and the robot ran to `max_steps` without ever moving (fixed: `343fa28`).
2. The bridge's staleness check compared action age against `STALE_OBSERVATION_S` (1.0s, meant for a
   synchronous loop) instead of `STALE_ACTION_S` (meant for real network round-trip latency), discarding
   every action as stale before it could execute (fixed: `e55aa53`).
3. `pop_validated_action()` in `robot_client.py` built `raw_action` from lerobot's own
   `_action_tensor_to_action_dict()`, whose keys are `.pos`-suffixed (`"shoulder_pan.pos"`), while
   `safety_validator.validate_action()` looks up plain `action_contract.JOINT_ORDER` names
   (`"shoulder_pan"`). Every joint silently failed the membership check, so `validated_action` came back
   `{}` for every real bridge action — not flagged as an error, just silently empty — and
   `robot.send_action({})` then crashed inside lerobot's own `ensure_safe_goal_position()` with
   `ValueError: max_relative_target keys must match those of goal_present_pos.` (fixed: `a3e16c4`).

With all three fixed, plus the safety-validator caps intentionally loosened this session (per an explicit
user decision — see §2) to let a real VLA action clear validation instead of being clamped
near-invisible, the episode ran end-to-end with no crash of any kind, upstream or otherwise.

## 2. Task 3: observed episode outcome

Episode recorded at `control/outputs/11-05-retry-20260924-120530/` (`episode.jsonl`,
`termination.json`, `camera_wrist/`, `camera_overhead/`) — the successful fourth live attempt this
session, following two earlier attempts that crashed on bugs #1 and #3 above (recorded in
`control/outputs/vla_episode_001/` and `control/outputs/11-05-retry-20260924-114555/`, both superseded
by this run). All numbers below are read directly from that `episode.jsonl`/`termination.json`.

- **Instruction:** "Pick the red cube and place it in the bowl" (matches the checkpoint's own trained
  task wording).
- **Termination:** `{"reason": "max_steps_reached", "steps_completed": 60}` — no crash, no e-stop
  trigger, ran to the configured cap.
- **Cube pick-up judgment:** not achieved as a completed pick-and-place — only one of the 60 steps
  executed a genuinely fresh model action (see below); the arm moved but the episode ended at
  `max_steps` mid-approach, not on a goal-met condition.
- **Step-by-step pattern (verified against the raw JSONL, not assumed):**
  - **Step 0:** action queue empty (Colab still cold-starting) — held, `model_version` suffix
    `"no action available, holding position"`.
  - **Steps 1–50:** a single 50-action chunk was being drained locally, but each real control tick took
    **10.9s–20.9s of wall-clock time** (avg ~12.9s) against a configured `control_hz=2.0` (i.e. an
    intended 0.5s/tick) — two orders of magnitude slower than configured. By the time each queued action
    was popped, it had already aged past the (intentionally loosened, per §2 below) 30s staleness cap, so
    **every one of these 50 actions was discarded**: `"stale observation (Ns > 30.0s), holding all
    joints"`, with `executed_action` identical to the prior `joint_state` (i.e. genuinely held, not
    silently substituted).
  - **Step 51:** queue reached empty — held one tick (`"no action available, holding position"`) while a
    fresh chunk was requested.
  - **Step 52:** the episode's only genuinely fresh, valid action executed. `validator_flags: []`,
    `model_version` suffix `"unknown"` (i.e. not a held/stale/no-action placeholder). Real joint deltas
    confirmed directly from `raw_model_output`/`executed_action`: `shoulder_pan` 2.7° → -5.6°,
    `shoulder_lift` -106.2° → -72.7° (33.4° move), `elbow_flex` 91.4° → 54.1° (37.4° move), `gripper`
    95.8% → 49.8% (46.0pp closing move). The physical arm visibly moved, confirmed by the human operator
    watching it live.
  - **Steps 53–59:** the second chunk immediately began going stale again — step 53 was already 36.8s
    old at pop time, just over the 30s cap — and every remaining step through 59 was discarded the same
    way as steps 1–50 (tick times 11.1s–28.3s, avg ~17.3s over this shorter tail).
  - **`validator_flags` was empty (`[]`) on every single step**, including all the discarded ones — the
    staleness discard happens in the bridge's own action-pop path (`STALE_ACTION_S` check), not inside
    `safety_validator.validate_action()`; the validator never had a chance to flag anything because
    every action it did see (steps 0, 51, 52 aside — step 52's only real action) was either a hold or the
    one clean pass-through.
  - **`latency_ms` was `{0, 0}` on every step** — this field is not yet populated by the bridge/client
    path; it is a known logging gap, not a real zero-latency measurement (the ~11–20s/tick durations
    above come from `timestamp_utc` deltas between consecutive JSONL records, not from this field).
  - **Net yield: 1 real executed VLA action out of 60 steps (1.7%).** The plan's own goal — "one full
    episode... recorded end-to-end" with real, non-scripted `episode.jsonl`/`termination.json` — is
    technically met (a complete 60-step run was recorded with genuine Colab-bridge output, not
    `"scripted-dry-run-v1"`), but the control loop is nowhere near continuous or smooth: for all but one
    tick, the robot held position while an already-stale action was discarded.
- **Safety validator caps loosened for this session:** per an explicit user decision (quick task
  `260924-e3d`, commits `d8c2785`/`8e2060a`), `safety_validator.py`'s per-step/velocity/staleness caps
  were loosened roughly 8–10x (max per-joint step 5°→40°, max velocity 30°/s→240°/s, `STALE_OBSERVATION_S`
  1.0s→10.0s, `STALE_ACTION_S` 3.0s→30.0s; gripper scaled similarly) specifically so a real VLA action
  could clear validation and actually execute, rather than being clamped near-invisible or discarded as
  stale, in this physically empty test environment. Even with a 30s staleness cap (10x the original), the
  observed ~11–20s/tick rate still discarded 59 of 60 actions — the loosening was necessary but not
  sufficient to fix the underlying tick-rate problem (see §5).

## 4. D-05 — no reasoning trace (explicit restatement)

Per `11-CONTEXT.md`'s D-05: **SmolVLA has no reasoning trace or tokens to capture.** It maps
observations directly to joint-position actions with no intermediate natural-language reasoning step,
unlike an LLM/MLLM. VLAHW-03's "complete I/O" framing — raw camera frames, joint state, task
instruction, raw model output, validated action, executed action, latency, model version, all captured
per step in `episode.jsonl` — is the **correct and complete substitute artifact** for this phase, not a
reduced/incomplete stand-in for a reasoning trace that doesn't exist. This is a settled non-decision, not
a phase gap: the next milestone phase (deep-reasoning MLLM comparison, §5) is where reasoning-trace
capture actually applies, and that phase should not re-litigate this framing.

## 5. Go/No-go recommendation for next milestone phases

**Recommendation: GO, conditional on one concrete, scoped engineering fix before the next live episode
attempt (in this phase or the next).**

The underlying pipeline — Colab-hosted PolicyServer → ngrok tunnel → `BridgeActionSource` →
`safety_validator` → real SO-101 → `IOLogger` — is proven to work end-to-end: it ran a full episode with
no crash, no upstream #2210 reproduction, and one confirmed real, valid, safety-validated VLA action that
visibly moved the physical arm exactly as the checkpoint predicted. All three bridge-code bugs that
blocked this from working are fixed and committed. That is sufficient evidence to proceed with the
milestone's next planned phases (deep-reasoning MLLM comparison, raw-autonomy design per
`.planning/REQUIREMENTS.md`'s Future Requirements section) rather than stopping to redesign the
architecture.

**However, the 1/60 (1.7%) real-action yield in Task 3's episode is not usable continuous control, and
the next phase should not repeat this episode blind to the concrete, scoped cause:**

- **The client re-sends a full camera observation to Colab over the ngrok tunnel on every control tick**
  (`control_loop_observation()` in the bridge path), even while it is only locally draining an
  already-fetched action chunk from a prior inference call. Each of those observation round-trips is
  what makes every tick take ~11–20s wall-clock instead of the configured 0.5s (`control_hz=2.0`) — by
  the time a queued action is popped, it is already staler than even the loosened 30s cap allows.
- **Concrete next engineering task (scoped, not aspirational):** change the client so it only sends a
  fresh observation / requests new inference when the local action queue is empty or near-empty, not on
  every tick while draining an already-fetched chunk — and/or reduce `control_hz` to a value that matches
  the realistically-achievable tick rate given actual Colab/ngrok network latency (measured this session
  at ~11–20s/tick, not the assumed 0.5s/tick). Either change (or both) directly targets the gap between
  "one action worked" (proven) and "actually usable continuous control" (not yet proven) — this is the
  scoped blocker to resolve before the next live-hardware attempt, not a call for a broader architecture
  change.
- Once tick latency is brought back in line with (or `control_hz` is tuned to) real network round-trip
  time, the now-loosened safety-validator caps (§2) should be revisited — they were loosened specifically
  to compensate for the staleness problem in this test environment, and a faster, more reliable tick loop
  may allow tightening them back toward their original, more conservative values.

**Bottom line:** the hardware-in-the-loop pipeline is real, safety-validated, and instrumented — the
architecture does not need to change. What blocks smooth continuous VLA control is a specific,
already-diagnosed latency bug in the observation-send cadence, not an open design question.
