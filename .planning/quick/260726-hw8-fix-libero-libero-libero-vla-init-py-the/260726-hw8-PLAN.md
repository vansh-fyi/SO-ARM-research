<objective>
Fix `libero/libero/libero/vla/__init__.py`'s two optional-import guards, which currently only catch `ImportError` and therefore fail to achieve their own documented purpose. Live on Colab (Notebook B, π0's separate kernel), `from .oft_backend import OFTBackend` raised `ValueError: numpy.dtype size changed, may indicate binary incompatibility` from deep inside `transformers`/`torch`'s import chain — not an `ImportError` — so it propagated uncaught and crashed the entire `libero.libero.vla` package import, taking `Pi0Backend` down with it even though `Pi0Backend` has nothing to do with `OFTBackend` and was the only thing that cell actually needed.

Purpose: Both guards' own inline comments state the identical intent — let this shared package import successfully in either kernel (Notebook A's OFT-stack kernel, Notebook B's openpi-stack kernel, or the local no-GPU pytest environment) even though only one backend's real dependencies are installed/compatible in any given kernel (D-06). `except ImportError:` only catches the "module literally absent" case (`ModuleNotFoundError`); it does not catch "module present but its transitive dependency chain is binary-incompatible with the numpy actually installed in this kernel" — the exact failure just observed live. Broadening to `except Exception:` on both guards (not just OFTBackend's, which is the one that failed) makes the code match what its own comments already claim it does, and defends symmetrically against the same class of failure hitting Pi0Backend's guard in Notebook A's kernel.
Output: A corrected `libero/libero/libero/vla/__init__.py` where both guards catch `Exception`, with updated inline comments noting the guard now also covers binary-incompatibility errors (numpy ABI mismatches) discovered live 2026-07-26 during Notebook B's VLA-04 smoke test. No other file changes.
</objective>
