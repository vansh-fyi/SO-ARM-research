**Why these specific new values (derivation, so the executor doesn't need to re-derive):**

- `MAX_RELATIVE_TARGET_DEG`: arm joints (`shoulder_pan`, `shoulder_lift`, `elbow_flex`, `wrist_flex`, `wrist_roll`) go from `5.0` to `40.0`; `gripper` goes from `15.0` to `60.0`. Both are within the user's requested ranges (30-45 deg arm, 50+ gripper) and stay well inside every joint's absolute hardware limit (e.g. `shoulder_pan`'s real limit is ±70.33 deg per the live calibration — computed from `control/test_safety_validator.py`'s `mock_calibration_file` fixture, which mirrors the real `soarm_follower_02.json` values — so the per-step cap can never itself push a joint anywhere the absolute clamp in step 2 wouldn't already allow).
- `MAX_VELOCITY_DEG_PER_S`: scaled by the exact same multiplier as the per-step cap for each group (arm: 5.0->40.0 is 8x, so 30.0->240.0; gripper: 15.0->60.0 is 4x, so 50.0->200.0). This preserves the original design's crossover dt (the dt below which the velocity cap starts binding tighter than the per-step cap) while scaling the whole envelope up — at the bridge's real dt_s=0.5s (both `run_vla_episode.py`'s default `--control-hz 2.0` and `BridgeActionSource`'s default `dt_s=0.5` land here), `MAX_VELOCITY_DEG_PER_S[joint] * 0.5` is `120` (arm) / `100` (gripper) — both comfortably above the new `40`/`60` per-step caps, so the velocity cap will not re-clamp a step the per-step cap already allowed at the real operating dt.
- `STALE_OBSERVATION_S`: `1.0` -> `10.0` (top of the user's suggested 5-10s range — biased generous per explicit instruction).
- `STALE_ACTION_S`: `3.0` -> `30.0` (top of the user's suggested 15-30s range — this is the constant `pop_validated_action()` in `robot_client.py` actually checks bridge-returned actions against; biased generous since discarding-as-stale was the directly-observed failure mode last session).

**Why 3 (not all 7) tests in `test_safety_validator.py` need updating:** `test_out_of_range_value_clamped_to_joint_limit` and `test_gripper_percent_value_not_treated_as_meters` don't exercise the per-step/velocity/staleness constants (their inputs stay within both old and new cap values), and `test_nan_value_holds_current_state_and_does_not_propagate` / `test_infinite_value_holds_current_state_and_does_not_propagate` test step 1 only — none of these need any change. Only `test_large_step_clamped_to_max_relative_target_default`, `test_velocity_cap_clamps_further_given_short_dt`, and `test_stale_observation_holds_all_joints` hardcode a result computed from an old constant value and will fail (or worse, silently stop testing the clamp path at all) once the constants change.
