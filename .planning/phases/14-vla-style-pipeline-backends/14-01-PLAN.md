<objective>
Lay the shared foundation Phase 14's 12 new backends all build on, without touching SmolVLA's live behavior: parameterize `connect_bridge()` with an optional `policy_type` (currently hardcoded to `"smolvla"`), and create the `control/vla_bridge/backends/` package -- an auto-discovering `BACKEND_REGISTRY`, a `BackendHandles` construction-result contract, and two shared per-tier helpers (`build_grpc_action_source()` for Tier A/B's gRPC-bridge lane, `HttpAdapterActionSource`/`build_http_adapter_backend()` for Tier C's resident-HTTP-adapter lane) that every later wave's thin per-backend module calls into.

This directly implements CONTEXT.md's D-04 ("refactor BridgeActionSource into a shared base... thin per-backend subclass... do not write 12 fully independent ActionSource classes, do not collapse into one config-only class") and PIPE-01's "existing SmolVLA integration fits the pattern unmodified" -- `BridgeActionSource` itself already has nothing SmolVLA-specific in it (confirmed by reading `robot_client.py` directly this session: it only stores a generic `client`/`checkpoint`/`joint_limits_deg`), so the actual refactor needed is narrow and low-risk: make the one hardcoded `policy_type="smolvla"` string in `connect_bridge()` a parameter, and build the registry/dispatch scaffolding around it and around a new Tier C HTTP-adapter counterpart. The two shared helpers built here (`build_grpc_action_source()`, `HttpAdapterActionSource`/`build_http_adapter_backend()`) are the concrete implementation of D-01's two transport lanes (gRPC bridge for Tier A/B, resident HTTP adapter for Tier C), refined into the 3-tier split 14-RESEARCH.md derived from D-01.

Depth stays completely out of scope for this plan and every backend built on it, per D-03: neither `build_grpc_action_source()` nor `HttpAdapterActionSource` touch `depth_camera.py`/`fastfs_server.py`/`depth_recorder.py` at all -- depth capture/recording remains exactly as `run_vla_episode.py`'s own `run_episode()` already handles it (log-only, never added to any backend's observation dict), regardless of which of the 13 VLA-style backends is selected.

Purpose: every later Phase 14 plan (Wave 2 onward) needs this scaffolding to exist first -- this is the plan that makes "which of the 3 known integration patterns does backend X need" (per 14-RESEARCH.md's key insight) a one-file, thin-module answer instead of hand-rolled plumbing per backend.
Output: `control/vla_bridge/backends/` package (registry + two shared helpers), `connect_bridge()` accepting `policy_type`, full regression-green existing test suite.
</objective>
