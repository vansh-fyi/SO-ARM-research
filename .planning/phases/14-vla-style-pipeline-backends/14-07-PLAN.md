<objective>
Integrate GR00T N1.7 (VLAB-10) as Tier B -- per 14-RESEARCH.md, GR00T N1.7 appears in `lerobot.policies`'s registry (training/loading support exists) but its presence in the async `PolicyServer`'s `policy_type` dispatch table specifically is UNCONFIRMED for this project's actually-installed `lerobot==0.6.1` (a live GitHub issue's error message -- not official docs -- lists a narrower confirmed set). This plan's first responsibility is resolving that uncertainty by reading the installed source directly (the same technique this project already used to resolve the `use_degrees` ambiguity in `action_contract.py`), then implementing whichever of the two known patterns (gRPC bridge, or Tier C HTTP adapter fallback) the verification result actually calls for -- not guessing.

Separately, GR00T N1.7 is architecturally different from N1.5: it uses a relative end-effector action space (not N1.5's absolute targets), shared across a 132-dimension cross-embodiment action vector per 14-RESEARCH.md's State of the Art section -- this project's SO-101 subset must be sliced out and converted via `eef_to_joint`'s IK before reaching `safety_validator.validate_action()`, exactly like the delta-EEF backends, even though GR00T N1.7 is not literally in the "delta-EEF" family named in the quality gate -- it is a relative-EE family with the same "convert before validating" requirement.

Purpose: proves the Tier B decision procedure (verify installed source before committing to a transport tier) that Wall-X (Plan 14-08) will repeat.
Output: `backends/groot_n17.py`, `relative_ee_conversion.py`, and (conditionally) `groot_n17_server.py`; at least one live-hardware-observed action.
</objective>
