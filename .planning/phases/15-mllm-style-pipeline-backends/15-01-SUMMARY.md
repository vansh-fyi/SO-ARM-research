# Phase 15 Plan 01: MLLM chunk-drain slice Summary

A scripted fake MLLM now runs through the real `run_episode` loop (MockRobot, real IOLogger, unmodified safety validator). `MllmActionSourceBase` asks the provider for a JSON chunk of N absolute joint targets, drains it one step per tick, holds the live joint state from the first malformed step to the end of the chunk, and writes one staged trace record per chunk. The schema comes from `action_contract`, the prompt is lint-clean, and `chunk_len`/`step_dt_s` come from a config file whose derivation is written down.

## What was built

- **`mllm_schema.py`**: builds the step object by looping `JOINT_ORDER`, taking units from `ACTION_UNITS`. It has no per-joint bounds and no `minItems`/`maxItems` (D-04). Top-level keys follow the staged order `task_restatement, plan, scene_claims, actions, task_complete` (D-10). Scene claims are `{claim, source enum, confidence enum}` (D-11). Every object is closed and fully required. `lint_schema_subset` enforces the cross-provider subset. Golden hash for N=20: `2e5e5f09...98f37e4`.
- **`mllm_prompt.py`**: builds the system prompt as headed sections (ROLE, OUTPUT, JOINTS AND UNITS, TIMING, optional PER-STEP CHANGE CAPS, INPUTS, COMPLETION, CONTROL, optional ARM KINEMATICS (URDF)).
  - Timing uses the measured 0.785 s step: 20 steps = 15.7 s (D-24).
  - Numeric caps appear only when `disclose_safety_caps` is true (D-16).
  - States that depth is aligned approximately, not pixel-exactly (D-26).
  - The depth wording changes with `depth_presentation`, and the heatmap colour scale is built from `depth.range_m` (D-28).
  - The user text carries the previous plan, or `none (this is the first call)` on the first call (D-09).
  - `lint_prompt_text` flags the words Claude refuses on (reasoning, thinking, trace, scratchpad, chain-of-thought) and movement-primitive names.
  - Golden template hash: `ce29b4ed...0202b37` (`mllm-prompt-1`).
- **`mllm_defaults.json`**: `chunk_len` 20 with a `chunk_len_derivation` object (measured Phase 12 timing, lower bound N>=10, upper bound N<=20, duty-cycle table, and the MLLM API latency that has not been measured yet). Also `step_dt_s` 0.785 with its evidence, `depth_presentation` both, a 24x32 depth grid, sampling 1.0/0.95, `max_consecutive_failed_calls` 3, and `timeout_s` 900.
- **`base_mllm.py`**:
  - Constants, contract dataclasses, `MLLM_BACKENDS` and `register_mllm_backend`.
  - `load_mllm_settings`: merges the defaults with a per-backend config one level deep and raises `SystemExit` naming the bad field.
  - `parse_chunk`: tolerates a code fence, uses the default `json.loads` so a NaN in step k keeps steps 0..k-1, rejects bool, NaN, Infinity and float overflow, holds a short chunk's missing tail, and drops extra steps.
  - `MllmActionSourceBase`: non-blocking inflight lock; one provider call per chunk; every whole-call failure enqueues N holds; secrets are redacted from error text and from the record. `last_details["mllm_call"]` is set on the refill tick and `chunk_ref` on every tick. Includes an optional recorder hook and `prev_chunk_tick_period_s`.
  - Imports no `lerobot`, `cv2` or provider SDK (an AST test checks this).
- **`fake_providers.py`**: shared test doubles. `ScriptedAdapter` raises `AssertionError` when its script runs out, so an unexpected paid call fails the test loudly.
- **`test_backend_registry.py`**: `MllmActionSourceBase` was added to the conformance list (Protocol signature check).

## Deviations from Plan

None in scope. Two implementation choices the plan left open:

- **`internal-error` hold reason.** Any unexpected exception inside refill enqueues N holds, so a code bug cannot trigger a paid call on every tick. This is defensive; it supports D-00c and T-15-02.
- **How malformed steps are logged.** A NaN or Infinity step is logged under a `malformed_step_json` string wrapper instead of as a raw dict, so `last_details` stays strict JSON (research Pitfall 6).
