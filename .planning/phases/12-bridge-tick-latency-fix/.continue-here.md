# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through actual live failure tonight, not speculation. Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: **cuDNN lazy-plugin-loading race with mid-session torch reinstalls** — cuDNN 9.x splits into plugin `.so` files (`libcudnn_graph.so`, etc.) that PyTorch `dlopen`s LAZILY on first real use, not at import time. Any Colab cell that does `pip install torch==<version>` (or otherwise mutates shared site-packages) WHILE a separate already-running process has imported torch but not yet triggered its cuDNN-dependent code path risks a silent on-disk file swap → native, uncatchable `SIGABRT` the moment that plugin finally loads. **Structural mitigation required**: any component installing its own pinned torch/cuDNN build (e.g. Fast-FoundationStereo) MUST use a fully isolated Python environment (`virtualenv`), never touching the shared site-packages another running process depends on. This is exactly what was fixed tonight in Step 7 of `control/vla_bridge/policy_server.ipynb` — do not revert it, do not "simplify" it back to a shared `pip install`.
- [ ] CONSTRAINT: **Never `apt-get install python3-venv` inside Colab for isolated-env needs** — Colab's OS-level `apt` `python3` alias resolves to a DIFFERENT (older, e.g. 3.10) version than the actual active interpreter (e.g. 3.12). `apt-get install python3-venv` fetches the wrong package version, which can 404 from the Ubuntu mirror, leaving the stdlib `venv` module's bundled `ensurepip` broken. Always use `pip install virtualenv` + `python -m virtualenv <path>` instead — it bundles its own pip/setuptools/wheel and needs no OS package at all.
- [ ] CONSTRAINT: **Depth capture currently blocks the robot control loop, and the fix is architectural, not GPU tier.** `control/run_vla_episode.py`'s main loop (~line 355-362) calls `depth_client.compute_depth()` SYNCHRONOUSLY. Fast-FoundationStereo's Step 8 Flask handler shells out via `subprocess.run()` to `scripts/run_demo.py` fresh on EVERY request — full process spawn + torch/cv2 re-import + full model-checkpoint reload from disk into GPU VRAM, every single call, zero persistence. This produces 15-70s per call, confirmed NOT GPU-bound (verified `torch.cuda.is_available() == True`, "NVIDIA L4" correctly detected inside the isolated venv — ruled out CPU fallback). **Do not attempt to fix this by upgrading to A100 or any bigger GPU — it will not help.** The real fix is a persistent, model-resident depth server (load the FastFS model ONCE at startup, same pattern `PolicyServer` already uses for SmolVLA, call inference in-process as a plain Python function instead of a per-request CLI subprocess).

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Long-running service launched as `threading.Thread` inside a notebook kernel | A crash inside it (OOM-kill, CUDA driver segfault, or the cuDNN issue above) silently kills the ENTIRE Jupyter/Colab kernel process — including sibling services (Flask depth server, tunnels) — with zero traceback, just "Kernel crashed." This was the actual behavior on every one of the 3 prior Test 7 attempts before tonight. | blocking | Any long-running service started from a notebook cell (PolicyServer, Flask depth server) MUST run as a genuine `subprocess.Popen`, never a `threading.Thread`. Already fixed for PolicyServer in Step 3 of `policy_server.ipynb` — do not regress. |
| Mid-session `pip install` mutating shared site-packages another running process depends on | See cuDNN constraint above — this is the general form of the bug, not specific to cuDNN. Any package that gets lazily `dlopen`'d or re-imported later in a long-running process is vulnerable to this if its files get overwritten mid-session by an unrelated install elsewhere in the same notebook/filesystem. | blocking | Isolate any component with its own pinned dependency versions into its own `virtualenv`, full stop — don't rely on install ordering or "run this before that" discipline, since re-runs and out-of-order execution (which happened live tonight — see below) break that assumption immediately. |
| Re-running cells out of original notebook order (e.g. Step 6 → Step 3 → Step 4, skipping/reordering relative to Step 7) | Before the virtualenv fix, this silently changed which torch/cuDNN build the re-launched PolicyServer subprocess picked up, since it just reads whatever's on disk at launch time — order-dependent correctness is fragile and WILL be violated in real usage (it happened by accident tonight, described by the user as "I accidentally ran step 6 and then reran step 3 and 4 again"). | advisory | The virtualenv isolation fix makes Step 3/6/7 order-independent by construction — this is exactly why it's the right fix, not just "reorder the cells and hope." |
