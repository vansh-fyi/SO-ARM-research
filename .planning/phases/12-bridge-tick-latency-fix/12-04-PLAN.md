<objective>
Close the third and most severe (blocker-severity) gap found in Phase 12's live-hardware UAT
re-verification episode (`.planning/phases/12-bridge-tick-latency-fix/12-UAT.md`), already
root-caused with an explicit fix direction: the Colab `PolicyServer`'s
`observations_similar()` filter (vendored `lerobot`, `policy_server.py`) silently drops every
observation once the robot holds still, unless the observation's `must_go` flag is `True`
(`_enqueue_observation()`'s `obs.must_go or ...` short-circuit). The client-side condition for
`must_go` to become `True` on the next `control_loop_observation()` call is
`self.must_go.is_set() and self.action_queue.empty()` -- in the live UAT run, this did not
reliably converge for 6+ minutes (steps ~192-241 of a 300-step episode showed `obs_age_s`
growing unbounded from 30s to 227s before finally recovering), with recovery depending
entirely on the vendored `lerobot` library's own internal event/queue-state timing, not on any
mechanism this project's own code controls.

Fix: add a staleness watchdog inside `vla_bridge/robot_client.py` -- THIS project's own code,
never the vendored `policy_server.py` -- that tracks consecutive stale/no-action results from
`pop_validated_action()` across ticks and, after `N` in a row, forces recovery directly by
clearing `client.action_queue` and setting `client.must_go` (a `threading.Event()`), so the
NEXT `control_loop_observation()` call sends an observation the server's own
`_enqueue_observation()` unconditionally processes, bypassing `observations_similar()` --
instead of waiting on the vendored library's internal recovery path to fire on its own.

This is a location-and-wire-up task in the same spirit as Plan 12-01's LATENCY-01/02/04 fixes:
the recovery mechanism (`must_go`/`action_queue`) is already fully diagnosed and already exists
in the vendored library; this task adds the missing trigger this project's own code controls,
without touching the vendored server.

Purpose: Prevent a multi-minute mid-episode deadlock from silently destroying most of a live
episode's real-action yield -- exactly the failure mode `LATENCY-04`'s success criterion
("measurably higher real action yield") is meant to guard against.
Output: `control/vla_bridge/robot_client.py` modified in place (one new function, one new
counter on `BridgeActionSource`); `control/test_robot_client.py` extended with deterministic,
hardware-free test coverage reproducing the observed stuck state.
</objective>
