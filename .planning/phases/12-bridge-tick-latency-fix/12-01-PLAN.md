## Phase Goal

**As a** researcher running live VLA episodes against the real SO-ARM101 over the Colab bridge, **I want to** the bridge to only request fresh inference when its local action queue is empty/near-empty (instead of resending a full camera observation every control tick) and to structurally prevent duplicate in-flight requests, **so that** the robot executes many real, non-stale actions per episode instead of discarding nearly all of them the way Phase 11's episode did (1 real action out of 60 steps).

<objective>
Fix the three request-cadence/race-safety defects in `control/vla_bridge/robot_client.py`
that caused Phase 11's live episode to discard 59 of 60 real actions as stale
(`control/vla_bridge/FINDINGS.md` §2): `BridgeActionSource.get_action()` currently calls
`control_loop_observation()` unconditionally on every tick instead of consulting the
vendored `lerobot` library's own already-installed, already-configured
`_ready_to_send_observation()` gate (LATENCY-01); `pop_validated_action()` never updates
`client.latest_action`, so the vendored library's own dedup/staleness logic never
functions as designed (LATENCY-02); and there is no structural guard against duplicate
in-flight observation requests if a future change (e.g. adding a call timeout) reintroduces
overlap (LATENCY-04, defensive insurance only per CONTEXT.md D-05 -- no active bug today).

This is a location-and-wire-up task, not a design task: the fix mechanism is already fully
diagnosed and the reference implementation already exists in the vendored `lerobot` source
this project deliberately does not call directly (see module docstring,
`control/vla_bridge/robot_client.py` lines 1-35, for why).

Purpose: Close the root cause of Phase 11's 1/60 real-action yield so the milestone's later
phases (13-17) build on a bridge that actually drives the robot with fresh model output most
of the time, not one that discards nearly everything as stale.
Output: `control/vla_bridge/robot_client.py` modified in place (three behavior changes, same
file); `control/test_robot_client.py` extended with deterministic, hardware-free test
coverage for all three, per CONTEXT.md D-06 ("writing/updating unit tests where feasible").
</objective>

| T-12-02 | Denial of Service | `_ready_to_send_observation()`'s `qsize()/action_chunk_size` division (vendored, Task 1) | low | accept | Vendored `RobotClient.__init__` initializes `action_chunk_size = -1` (never `0`) until a real chunk arrives, confirmed by reading the installed `lerobot` source directly -- no `ZeroDivisionError` path exists for this call; verified-safe existing vendored-library invariant, not something this plan's code introduces or can violate. |
