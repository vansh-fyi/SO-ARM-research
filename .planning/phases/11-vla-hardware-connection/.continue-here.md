# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: **Do not send any motion command to the follower arm (no e-stop retest, no live episode, no `keyboard_joint_control.py`, nothing) until its on-servo calibration is verified/restored.** This session's live run of `detect_devices.py` almost certainly wrote the LEADER's saved calibration (Homing_Offset, Min_Position_Limit, Max_Position_Limit) onto the FOLLOWER's real servos — see full trace below. Follower and leader are physically different builds; their calibration ranges are not interchangeable. Sending motion commands before this is checked risks driving the follower outside its true safe range using the wrong limits.
- [ ] CONSTRAINT: **`detect_devices.py`'s `resolve_port_identity()` is not a reliable identity test and must not be re-run as-is.** It treats "connect + `write_calibration()` completes without raising" as proof that a port belongs to a given robot id. This is false — a wrong calibration file can write successfully to the wrong physical arm if motor IDs/ranges happen to overlap enough not to throw. This is what caused the follower/leader mixup this session, silently, mid-detection-loop, with no distinct error message at the time it happened (the bug was only found by carefully re-tracing which warnings were and weren't printed).

**Do not proceed until both boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Identity test using "write succeeded" as the signal | `resolve_port_identity()` (in `control/detect_devices.py`, worktree commit `fa99468`) calls `robot.connect(calibrate=False)` + `bus.write_calibration(robot.calibration)` and treats "no exception" as proof the port belongs to that robot id. On real hardware this session, the follower's port failed the follower-id check (comms error on motor 5) but then SUCCEEDED against the LEADER id — meaning it silently wrote the leader's calibration onto the follower's servos | blocking | Before `detect_devices.py` is trusted again: change `resolve_port_identity()` to verify something that actually distinguishes the two arms (e.g. read back a value after write and check it lands in the *expected* robot's known-good range, or use a lower-risk read-only probe — like reading `Present_Position` or a serial/model number register — before ever writing calibration data). Do not re-run the current version against real hardware. |
| Assuming "no warning printed" means "no attempt was made" | When manually tracing `detect_devices.py`'s output, my first read of the transcript concluded (wrongly) that the follower's servo id 5 had a bad cable — I hadn't noticed `resolve_port_identity()` only prints on FAILURE, so a *missing* warning for the leader-id check on the follower's port was actually a silent SUCCESS, not "it wasn't tried." The user caught this ("I call bullshit, read the output") before I acted on the wrong diagnosis. | advisory | When debugging a script with print-on-failure/silent-on-success logging, count expected message pairs against what's actually printed before concluding what happened — a gap in expected output is itself a signal, not just an absence. |
