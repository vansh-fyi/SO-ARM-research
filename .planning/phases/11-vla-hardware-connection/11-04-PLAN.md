<objective>
Wire a real, network-bridged SmolVLA policy into `run_vla_episode.py` by wrapping the installed `lerobot.async_inference.RobotClient` (the D-01 Colab-GPU-relay bridge) — but NOT via its own `control_loop()`/`control_loop_action()` methods, since those call `robot.send_action()` internally without passing through Plan 11-01's safety validator. This plan's core engineering task is bridging that gap: using the library's public queue/observation primitives while keeping every actual servo write gated by `safety_validator.validate_action()`.

Purpose: VLAHW-02 requires "VLA output actions pass a safety validator ... before being sent to the real robot" — this is only true if the integration explicitly avoids the stock `RobotClient.control_loop_action()` shortcut, which this session's direct reading of the installed `lerobot==0.6.1` source (not just its CLI docs) revealed writes to the servo unvalidated. Getting this wrong would silently violate VLAHW-02 while looking like it works.
Output: `control/vla_bridge/robot_client.py` (the validated bridge wrapper) and `run_vla_episode.py` extended with `--server-address`/`--checkpoint` flags that swap in the real bridge.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gRPC bridge (Colab PolicyServer ↔ local RobotClient) | Any action arriving over this tunnel is untrusted input to the safety validator, exactly like a local scripted source — the network does not make it more or less trustworthy |
| RobotClient's internal robot connection ↔ our validation gate | The installed library's own `control_loop_action()`/`control_loop()` bypass any external validator; this plan's entire design exists to prevent that bypass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-09 | Tampering | any action arriving over the gRPC bridge | critical | mitigate | `BridgeActionSource` routes every bridge-returned action through `pop_validated_action()` → `safety_validator.validate_action()` before any `send_action()` call; `control_loop_action()`/`control_loop()` (which call `send_action()` internally, unvalidated) are explicitly never called — `test_robot_client.py` pins this by construction (the fake client's `send_action` is never invoked from `pop_validated_action`) |
| T-11-10 | Tampering | stale bridge response after a network stall | high | mitigate | `pop_validated_action()` computes `obs_age_s` from `time.time() - timed_action.get_timestamp()` and passes it to `validate_action()`, which holds position wholesale once `STALE_OBSERVATION_S`/`STALE_ACTION_S` is exceeded (Plan 11-01) |
| T-11-11 | Denial of Service | unreachable/dead Colab bridge | medium | mitigate | `connect_bridge()` returns `None` (not an exception) on a failed handshake; `run_vla_episode.py` writes an explicit `bridge_unreachable` termination reason rather than attempting to drive the robot with a non-functional source |

</threat_model>
